## Experiment: E-046 — The board could name work that does not exist: CHECK 6's promise to resolve every sprint-status story against the records was never implemented

- **Date:** 15.10.2026
- **Status:** completed
- **Theory:** `check-methodology.sh` CHECK 6 has opened, since the counting was written, with the comment "Check if there are stories in sprint-status that lack methodology records". Nothing implemented it. The board's story keys were only ever COUNTED (in-progress, done) and the `# Methodology record:` pointer list checked the sprint records beside them; the keys themselves were never resolved against anything. That matters because every chain rule in the engine starts from a story FILE and looks outward (`_iter_story_files` → `_story_key_of` → QR/methodology/SP records), so a key the board carries with no story behind it is invisible to all of them. Measured 2026-10-15 on a project whose board carried `9-9-ghost-story-that-does-not-exist` in `in-progress`: the gates (`_find_done_stories_without_qr/ir/sp`, the story-quality scan) returned nothing, `check-methodology.sh` never printed the key anywhere (`grep -c 9-9` = 0), and the only trace of it was `There are 1 in-progress stories — verify methodology records exist` — a nudge to go verify records for a story that does not exist, while the real in-progress count was zero. The same script also demonstrated the defect on the plugin's own tree the moment the rule landed: the board shipped in d29218c named `1-1-change-radar-contract-measured` and the record for that story (S-001) declared no such key, so the board and the record were two names for one piece of work with nothing pinning them together. The class is the project's recurring one (E-037): an artifact asserting a fact nobody measured — here the board asserting that work exists. The closure resolves every board key through the ENGINE's own vocabulary (`guard.board_story_keys_without_records`: a story file named by the key by field/title/filename, or a record that DECLARES it with the declared-label rule the write-time gate applies) and reports an unresolved key as an issue, which is what makes the opening comment true. One measurement forced the rule tighter while closing: the first version resolved the key from a prose mention, because it reused `_story_key_of`'s last fallback (an `N-N-slug` anywhere in the body) — a record whose regression note named a since-renamed story therefore "covered" that board key, so the identity is now field/title/filename only (`_board_key_identity`) and a mention cannot pass as a record.
- **Hypothesis:** H-046: "consistency_accuracy >= 0.90"
- **Measurement Metrics:** consistency_accuracy >= 0.90
- **Experiment Design:** Inputs — the plugin repository at this commit. Procedure — run `python scripts/bench/bench_consistency.py`; the new check `_check_board_story_keys_resolve` derives the board's story keys from the tree (same grammar CHECK 6 and the engine count), asks the engine to resolve them on the shipped tree, then drives the real audit script against a temporary project whose board carries a phantom key and requires the script to raise an ISSUE that NAMES it (a warning, a bare mention or silence all fail). Controls — the falsifier ran red BEFORE the fix: on the phantom fixture `guard.board_story_keys_without_records` returned `[]` and the audit printed the key nowhere, and after the fix the same fixture yields `['9-9-ghost-story-that-does-not-exist']` from the engine and `❌ ISSUE: sprint-status.yaml names story '9-9-ghost-story-that-does-not-exist' …` from the script; on the plugin's own tree the new rule fired against the shipped board (`1-1-change-radar-contract-measured` declared by no record) and went clean once S-001 declared it, so the closure is proven on real content and not only on a fixture. Reproducibility — stdlib only, no network, deterministic (text plus one engine call).
