## Experiment: E-096 — A multi-entry migration is one transaction

- **Date:** 31.10.2026
- **Status:** completed
- **Theory:** E-095 made the index rebuild part of the mutation's transaction for `finalize` and `discard`, and its own Known Gaps named what was still open: "a multi-entry writer (`migrate`) still commits entries one at a time — a failure mid-migration leaves earlier entries migrated and later ones not". A probe on this host reproduced exactly that. A registry with two schema-1 entries (`alpha`, `beta`) and an `atomic_write_text` that raises `OSError: [Errno 28] No space left on device` on its second call reported `schema before: 1 1`, raised the error, and left `schema after : 2 1`: the first entry was upgraded, the second was not, and the registry is now a mixture of two schemas that no command describes. The theory under test is that a schema migration is one transaction over every eligible entry — all candidates are built before the first write, and a failed write restores the entries already written byte for byte — while a migration that can complete still upgrades every eligible entry exactly once and leaves current-schema entries untouched.
- **Hypothesis:** H-096: "consistency_accuracy >= 0.90"
- **Measurement Metrics:** consistency_accuracy >= 0.90
- **Experiment Design:** Measure the focused migration bench `scripts/bench/bench_external_context_migration.py`: two rollback cases (two legacy entries where the second write fails; three legacy entries where the third write fails) that must leave every entry byte-identical, plus four controls a migration that writes nothing at all would also fail — the first write failing before anything was written, a `--dry-run` that plans two upgrades and writes neither, a schema-2 entry that stays byte-identical while its legacy sibling is upgraded, and a normal run that upgrades both and reports a no-op on the second run. The `--broken` control disables the rollback helper in memory, reproducing the pre-E-096 order: the two rollback cases keep a half-migrated registry while the four controls still pass. Replace the write-as-you-plan loop in `migrate` with one plan built inside the registry lock for every eligible entry, then a single write pass that records each entry's exact pre-write bytes and, on any failure, restores the written entries in reverse order before re-raising. Read failures already happened in the plan phase, so a read error cannot leave a half-written registry. Pin the rollback, the whole-plan upgrade with a no-op second run, the dry run and the current-schema control with unit tests, one consistency-bench contract, and the focused bench. Reproducibility is local, deterministic and offline.
- **Sample Size n:** measured from the bench output
- **Code Scope:** scripts/external-context.py, scripts/bench/bench_consistency.py, scripts/bench/bench_external_context_migration.py, scripts/tests/test_external_context.py, docs/experiments/E-096.md
- **Lineage:** E-095 (the record whose Known Gaps named this open writer, and whose preflight/rollback pattern this reuses), E-092 (the registry's transactional guarantee this extends from one entry to a whole migration), E-094 (the immediately preceding registry hardening), E-089 (the shared module and atomic writes) — this record inherits their transaction, boundary and determinism guarantees and closes the multi-entry half they left open.

The migration stays mechanical — it adds the fields and the revision row a schema-1 entry lacks and does not run the validator, so an entry `check` rejects before a migration can still be rejected after it. The "unreadable entry" half of the claim is held by ordering (the plan phase reads every entry before the first write) rather than by a bench case, because the bench cannot make a read fail deterministically without a second monkeypatch. The two rollback cases share one code path (`migrate`'s write pass), so n=6 is a small sample and the gate's Wilson bound may keep it advisory.
