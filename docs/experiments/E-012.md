## Experiment: E-012 — The release number is the commit's position: repair the drifted chain and make the CI derive it absolutely

- **Date:** 09.10.2026
- **Status:** completed
- **Theory:** Reading the real history (not the claims about it) is the same
  discipline the audit class of E-001 demanded, applied to the release number
  itself. The chain had 13 commits, one tag per hand (v0.1.0 on the first
  commit, v0.1.5 on the tenth) and a version string that had drifted six
  numbers behind the position the head commit actually held: commits #1..#9
  shipped saying 0.1.0, #10 and #11 said 0.1.5, and the CI's own first bump
  left 0.1.6 on #13. Two facts make this mechanical rather than a matter of
  taste. (1) The number is a property of the commit — the count of commits
  after the first one — so it can be derived from git and checked by anyone.
  (2) A relative bump (`--by N`, E-010) can only ever preserve whatever offset
  the tree had; making the offset disappear requires an ABSOLUTE target, which
  is why the CI must compute the number from the history instead of adding to
  a number it finds. The past itself cannot be un-committed: rewriting the 13
  commits would give every tree its own correct number at the price of every
  SHA anyone has ever seen (and every published tag), so the pointers are
  republished instead and the one place where pointer and tree disagree is
  written down (`docs/VERSION-HISTORY.md`) rather than hidden.
- **Hypothesis:** H-012: "consistency_accuracy >= 0.90"
- **Measurement Metrics:** consistency_accuracy >= 0.90
- **Experiment Design:** Inputs — the plugin repository at this commit, and its
  own git history and tags. Procedure — run
  `python scripts/bench/bench_consistency.py`, which evaluates independent
  doc/code-consistency claims and prints `consistency_accuracy=(x/y)`; three
  new checks pin the E-012 claim (the workflow derives the target from git with
  `--set-patch` and refuses to publish a tag whose number is not the commit's
  position, and every release tag in this repo sits at the position its number
  names with no holes in the chain; the rule, the retro-assignment and the
  re-pointed v0.1.5 are documented; and the repair tool plus the absolute rule
  stay covered by tests). Control — the bench's own "pytest suite green
  (falsifier)" check pins that the code under test still passes the full suite.
  Reproducibility — stdlib + git only, no network (the tag push is a separate,
  explicit `--push`), deterministic: `scripts/release-tags.py --plan` prints the
  same mapping on any clone, and the bench reads the tree and its refs as they
  are, independent of this record (E-001).
- **Sample Size n:** 68 (informational — the gate parses the denominator from

- **Known Gaps:** the retro-assigned tags record a commit's POSITION, not the
  version string inside that tree — for the eleven trees written before the
  rule had an owner they disagree (they say 0.1.0/0.1.5), and that disagreement
  is the price of not rewriting published history (it is tabulated in
  docs/VERSION-HISTORY.md). Re-pointing v0.1.5 is a rewrite of a published
  ref: the remote no longer serves the old target, but a clone that fetched it
  keeps the old object until it re-fetches with --force. The baseline v0.1.0 is
  a lightweight tag (created before this rule); the rule checks a tag's target,
  not its kind, and converting it would be another published rewrite. A push
  carrying N commits still leaves the N-1 intermediate commits on the number
  their author wrote (only the final commit's number is authoritative) and only
  the resulting release point gets a tag — server-side versioning cannot number
  an intermediate commit, and the repaired chain's no-holes rule therefore only
  constrains the tags that exist. Tags are pushed separately from commits, so
  the bench's chain check may legitimately stop short of HEAD; it fails on a
  MISPLACED tag or a HOLE, never on an unpublished tail. The repair itself is a
  one-time operation performed with push rights (scripts/release-tags.py
  --apply --move-mismatched --push) and cannot be repeated blindly: it refuses
  without --move-mismatched, and it never rewrites a commit.
