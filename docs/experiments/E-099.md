## Experiment: E-099 — The SkillOpt lane honours SkillOpt's own config, not a wrapper paraphrase

- **Date:** 02.11.2026
- **Status:** completed
- **Theory:** E-098 corrected the Hermit export from Hermit's field reference, but its SkillOpt lane only described SkillOpt *inside* Hermit (`evolver.name: skillopt` with Hermit's eighteen wrapper parameters). Reading `microsoft/SkillOpt/docs/` directly shows that a native SkillOpt run is a different contract. (1) One structured YAML with six sections — `model`, `train`, `gradient`, `optimizer`, `evaluation`, `env` — resolved from `configs/_base_/default.yaml` and overridden with `--cfg-options section.key=value`; the fields and defaults are enumerated in `reference/config.md`, including `optimizer.learning_rate` as the maximum number of edit patches per step, `lr_scheduler` in `constant|linear|cosine|autonomous`, `skill_update_mode`, `slow_update_gate_with_selection`, and `env.split_mode` in `ratio|split_dir` with `split_ratio`, `split_seed`, `data_path`, `skill_init`, `out_root`. (2) The CLI is `skillopt-train`/`scripts/train.py` and `skillopt-eval`/`scripts/eval_only.py`, with `--split train|valid_seen|valid_unseen|all` and a separate timestamped eval directory. (3) The skill document has two trainer-owned regions, `<!-- SLOW_UPDATE_START -->…<!-- SLOW_UPDATE_END -->` and `<!-- APPENDIX_START -->…<!-- APPENDIX_END -->`, which a patch must not rewrite; the slow update and the skill-aware appendix own them. E-098's lane had no native config, no split hand-off, no initial skill, no `skill_init` target and no protected-region rule: a learner could silently rewrite the longitudinal record and the export could still validate. The theory under test is that a native lane can be emitted and validated offline against the documented field set, and that the kernel's edit engine can enforce the trainer's region ownership before a candidate is measured — without weakening any earlier Hermit check.
- **Hypothesis:** H-099: "optimization_accuracy >= 0.90"
- **Measurement Metrics:** optimization_accuracy >= 0.90
- **Experiment Design:** Measure `scripts/bench/bench_optimization.py`, extended from 78 to 94 independent checks. The 16 new checks cover the native contract and the protected-region rule: the exported config has exactly the six documented sections in order; every key validates against the documented field table (including runnable invariants: `env.name`, `env.skill_init`, `env.data_path` under `ratio`); an unknown key (`train.epochz`), an unknown section (`optimiser`) and an out-of-set enum (`lr_scheduler: vibes`) are each refused; `optimizer.learning_rate` equals `gate.max_hunks` with `1 <= min_learning_rate <= learning_rate` and the slow update enabled; `env.split_ratio` equals the actual train/val/heldout sizes with `env.split_seed` equal to the run seed, and `valid_unseen.jsonl` has exactly the held-out count; `env.skill_init` resolves to the same bytes as version `v0000`; `best_skill.md` equals the latest accepted version and matches the manifest sha256; the README names `--split valid_seen` and `--split valid_unseen` and the manifest records both; editing `best_skill.md` after measurement is detected as a sha256 mismatch; both protected regions parse with their bodies intact; an unbalanced marker pair is flagged; an edit inside a region, an edit that deletes a marker and an edit outside a region are respectively refused, refused and allowed. The `--broken` control removes the native config from the bundle and returns false from the schema checks, so the same 94 assertions run against the pre-correction behaviour. Offline, stdlib only, deterministic.

- **Known Gaps:** Validation is schema-level, not a live SkillOpt install: key names, enums, defaults, runnable invariants, split names and protected markers are checked, but whether a given SkillOpt release accepts every value can only be established by running `skillopt-train` in that environment, which this repo cannot do offline. `model` is validated by documented key families rather than an exhaustive list, because its backend-specific surface changes between releases. The native bundle is not a benchmark reproduction: it needs the environment adapter for these cases (task fields, judge, answer parsing), so `env.split_mode` stays `ratio` and the materialized split files are a hand-off, not a claimed `split_dir` contract. Protected regions are enforced structurally; the kernel does not itself run SkillOpt's slow update, so a region body is preserved rather than generated. The bench's broken control degrades production paths in memory, so it proves the checks can fail, not that an independent SkillOpt implementation would behave identically.
