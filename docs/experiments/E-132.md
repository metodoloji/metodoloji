## Experiment: E-132 — The freshness scan re-derives a regex 114,000 times and blows the hook budget

- **Date:** 2026-11-12
- **Status:** completed
- **Record Kind:** experiment
- **Theory:** The freshness plane re-derives a verdict for every APPROVED record on every write-shaped command. Downstream (m-tesil, E-102) that scan made every commit attempt fail with a methodology pre-hook timeout while the engine verdict was allow; profiling put 13.1s of 21.7s inside glob_to_regex: 114,109 calls with only 248 distinct patterns, a pure string function with no memoisation, invoked from scope_matches once per record-and-file pair. This repository is the same engine one order larger (127 experiment records), and the shipped engine here answers a write-shaped payload in 32.7s against a 10s hooks.json PreToolUse timeout and a 12s adapter budget: this project cannot land a change through its own gate, and every downstream project reaches the same wall as its record count grows. The defect is not IO: one diff on this tree costs 44ms and there are about a hundred of them. It is a hot loop re-parsing 248 patterns 114,000 times because nothing caches the parse.
- **Hypothesis:** H-132: "freshness_scan_over_budget_rate >= 0.999"
- **Measurement Metrics:** freshness_scan_over_budget_rate >= 0.999
- **Experiment Design:** Four cells: the shipped engine driven with a write-shaped payload in both modes the adapter calls (pre, quality) and both message forms (-m, -F), each scored on one question - did the engine return a decision inside the tightest runtime budget (10s hooks.json, the stricter of 10s and 12s)? A cell is over-budget when elapsed exceeds it, because that is the condition where the runtime discards the answer and fails closed. Each cell records the engine verdict beside its time, since a gate denial and a gate that never got to answer are different facts that the current UX collapses. The rate is the share that are over-budget. The control runs the identical engine on a command that is not write-shaped, where the freshness plane is skipped entirely, and must finish inside the budget - proving the budget is adequate for the hook ordinary work and the overrun belongs to this scan.

- **Known Gaps:** This record measures the overrun and authorises the repair of freshness.py; it does not decide the repair shape. Three variants were measured downstream and only one is worth landing: caching glob_to_regex alone recovers 1.6-1.8x, caching scope_matches on top makes it worse on a real corpus (4,041 hits against 28,094 misses - the predicate sees a different scope-and-path pair almost every time), and pre-compiling the pattern adds nothing because re already caches compiled strings internally. The fix is therefore one decorator on the pure function, and the verification record owns proving it changes no verdict. A second limit: raising the budget is not a fix. Cost is linear in record count, so any budget is a wall the next hundred records reach; the plan must name the algorithmic repair, not a bigger number. A third: after the decorator the scan is expected to land near 6s on the downstream corpus, which is under budget but still linear - the cache removes the redundancy, not the growth.
