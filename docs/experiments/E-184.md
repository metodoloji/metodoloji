## Experiment: E-184 — A destination carried by a flag is still a destination

- **Date:** 2026-11-20
- **Status:** completed
- **Record Kind:** experiment
- **Theory:** The guard gates what bash_targets names: a command word that yields no target is judged as a read. Probing the shipped extractor (2026-11-20) found that cp/mv/install/ln spell the destination in a -t/--target-directory flag (leaving only the SOURCE as an operand, so the last-operand rule named a read), and that separator-less git checkout names its path only after a revision: git checkout P and git checkout HEAD P rewrote the working tree while git checkout -- P and git restore P are denied.
- **Hypothesis:** H-184: "flag_target_accuracy == 1.0"
- **Measurement Metrics:** flag_target_accuracy == 1.0
- **Experiment Design:** Inputs: the shipped hooks/engine/modules/bash_targets.py and the pre-E-184 tree at git 55c8608. Procedure: scripts/bench/bench_write_target_flags.py drives guard() in its own process over eighteen commands against a gated code path (src/zzz_probe.py): nine writes whose destination rides a flag or follows a revision, three already-denied twins (the operand spelling, the -- spelling, and rsync -t whose flag means preserve-times), and six non-writes that must stay allowed (git checkout main, git checkout -b, git checkout HEAD~2, two out-of-tree destinations, a listing). Control: --broken runs the same eighteen probes against 55c8608, where the flag and revision spellings name no target. Reproducibility: stdlib only, offline, deterministic; every probe is a fixed string and its expected verdict is stated once.
