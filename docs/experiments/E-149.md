## Experiment: E-149 — Retire the `bmad/` tree: every file moves next to its owner

- **Date:** 2026-11-13
- **Status:** planned
- **Record Kind:** contract
- **Theory:** `bmad/` is the last directory in the plugin that names no owner. It holds six CLIs (`blackboard`, `orient`, `resolve_config`, `resolve_customization`, `skeleton`, `workflow`), the workflow kernel package (`bmad/workflow/`, 6 modules + 2 builtin specs), seven test files, and five catalog CSVs — three of which (`bmb|bmm|core/module-help.csv`) have no reader at all and whose rows are a stale subset of `_config/bmad-help.csv`. Because tooling, data and tests shared one directory, every rule had to special-case it: `config.py:470` frees `hooks/`, `scripts/`, `skills/` but explicitly keeps "bmad/ workflows gated"; `check-techdebt.sh:335` carries a `$PLUGIN_ROOT/bmad` scan root; `check-plugin.sh` §6d2 greps every command for `bmad/scripts/*.py`; `bench_consistency.py` asserts the scan roots include `bmad`; and 91 live files spell the CLI paths. None of that is about BMad compatibility — `blackboard.py` is not more BMad than `hooks/`. The move is nearly free because `bmad/scripts/X.py` and `hooks/scripts/X.py` sit at the SAME depth from the plugin root, so every `parent.parent` / `parents[2]` / `parent.parent.parent` in the moved CLIs keeps resolving the plugin root unchanged. What actually changes is eleven lines: seven `from bmad.workflow import` statements, `workflow.py`'s builtin directory, the `hooks/engine/resolve_customization.py` shim target, and the free-zone policy.
- **Hypothesis:** H-149: "bmad_retirement_accuracy == 1.0"
- **Measurement Metrics:** bmad_retirement_accuracy == 1.0

## Implementation Plan (GRP)

### A. Three decisions this plan takes

The survey left three questions open. Each is one revertible step; the plan proceeds on the recommendation and names the revert cost.

**A1. Guard free-zone shift — ACCEPT.**
`bmad/scripts/` is gated today (`config.py:470`: "bmad/ workflows stay gated"). After the move the six CLIs sit under `hooks/scripts/`, which `PLUGIN_FREE_PREFIXES` frees *when the project root is the methodology root* (self-modification). This is the correct end state: the exception existed only because `bmad/` also held content (workflow specs, catalogs), and tooling does not belong behind the gate the tooling enforces. In a consumer project nothing changes — the plugin tree is not at the project root, so neither prefix applies. Check 7 proves no path outside the moved set changed verdict.
*Revert cost:* one tuple entry in `config.py` plus `test_config.py:71`.

**A2. `skill-manifest.csv` → `skills/skill-manifest.csv`.**
It describes `skills/`, so it lives there. *Risk, stated plainly:* `bench_consistency.py:2967` calls it "the catalogue a BMAD installer reads". If an external installer hardcodes `bmad/_config/skill-manifest.csv`, that contract breaks. No in-repo reader does so outside the checks this plan updates.
*Revert cost:* `git mv` one file back plus four path constants. **If the external contract is real, this is the one sub-step to split out** — keep that file where it is and retire everything else.

**A3. The three `module-help.csv` files — DELETE, do not move.**
Verified against the tree: `bmb` 4/4, `core` 13/13, `bmm` 23/24 rows are byte-identical to rows already in `_config/bmad-help.csv`. The single `bmm` difference is `bmad-sprint-planning`, where `bmad-help.csv` carries a *newer* description that also names the SP gate record. Their only "reader" is a filename in `bench_skill_removal.py`'s probe list. Moving three stale copies into `skills/` would create three new duplicate-owner surfaces on the day the repo closes that class.
*Revert cost:* `git checkout` three files.
