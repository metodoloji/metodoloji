## Experiment: E-011 — The version-only CI cuts the release tag: a bump nobody can point at is not a release

- **Date:** 09.10.2026
- **Status:** completed
- **Theory:** First-run evidence from the E-010 instrument (the pipeline really
  fired: push → CI → 0.1.5 → 0.1.6 on main). That run exposed the missing half:
  the version moved but no `v0.1.6` exists — `git tag` still ends at `v0.1.5`,
  cut by hand. A version number without a tag is a claim nobody can point at:
  the marketplace cache, the README badge and `pyproject.toml` all say 0.1.6,
  while the release history the chain relies on (v0.1.0, v0.1.5, each an
  immutable pointer to a shipped tree) stops one hop behind reality. The
  methodology's own rule for evidence applies here — an artifact must be
  checkable by a stranger — and a tag is the only checkable form of "this tree
  was version 0.1.6". The instrument already knows the new version (it just
  wrote it), so the fix is to let it publish the pointer in the same run: tag
  HEAD with `v<version>` AFTER the bump commit is pushed, never before (a tag
  on the parent commit would point at the pre-bump tree — a permanently wrong
  release). Tag creation is idempotent against re-runs and refuses to move an
  existing tag: history is append-only.
- **Hypothesis:** H-011: "consistency_accuracy >= 0.90"
- **Measurement Metrics:** consistency_accuracy >= 0.90
- **Experiment Design:** Inputs — the plugin repository at this commit.
  Procedure — run `python scripts/bench/bench_consistency.py`, which evaluates
  independent doc/code-consistency claims and prints
  `consistency_accuracy=(x/y)`; two new checks pin the E-011 claim (the
  workflow derives the tag name from the bump script's own output
  (`--print-version`), creates an annotated tag, pushes it, and does so in a
  step that runs AFTER the bump commit is on main and honours the same
  `[skip-version]` guard; while README/GUIDE/KILAVUZ state that CI tags the
  release; and the tag seam stays covered by tests). Control — the bench's own
  "pytest suite green (falsifier)" check pins that the code under test still
  passes the full suite. Reproducibility — stdlib only, no network,
  deterministic (a fixed tree yields a fixed x/y); the measurement reports the
  tree as it is, independent of this record (E-001).
- **Sample Size n:** 65 (informational — the gate parses the denominator from

- **Code Scope:** .github/workflows/version-bump.yml, scripts/bump-version.py, scripts/tests/test_bump_version.py, scripts/bench/bench_consistency.py, README.md, GUIDE.md, KILAVUZ.md

- **Known Gaps:** the tag is cut on pushes to main only, like the bump itself —
  a branch-only commit still tags nothing (by design: a tag on an unmerged
  branch is a release nobody can reproduce). The tag step cannot repair the
  version that the PREVIOUS run already bumped without a tag (this experiment
  is the instrument's own hole: 0.1.6 is on main, untagged, and no future run
  can safely guess it was meant to be a release — back-filling it is a human
  decision, taken outside the pipeline). If the tag already exists remotely at
  a DIFFERENT commit, `git push origin refs/tags/<tag>` is rejected and the job
  goes RED — loud, never a silent re-point of shipped history. If the tag
  already exists at the same commit (a re-run after the bump step succeeded but
  the tag push failed), the push is a no-op success instead of a second tag.
  Branch protection that blocks tag pushes turns the job red for the same
  reason as the E-010 push rule: enforcement is visible. The audits still stay
  local — this CI never runs them.
