## Experiment: E-098 — The training export matches Hermit 0.1.0 field by field

- **Date:** 02.11.2026
- **Status:** completed
- **Theory:** E-097 built an optimizer whose export was described as following "the documented shape" of Hermit, but the shape was inferred from a repository README and a rendered project page, not from the field reference. Reading the actual 0.1.0 documentation and examples showed four concrete mismatches. (1) Hermit's `run.yaml` is not a flat `{name, method, adapter, tasks, judge, gate}` document: it has `data` (`tasks`, `train`, `val`, `test`, `step_size`, `shuffle`, `shuffle_seed`, `task_info`), `template`, `evolver` (`name`, `params`, `resume`), `agent` (`name`, `concurrency`), `judge` (`path`, `name`), optional `llm`/`sandbox`/`start_from`, and `trainer` (`run_name`, `output_dir`, `tree_dir`, `epochs`, `budget`, `call_timeout_min`, `resume_mode`); unknown framework keys are rejected. (2) Splits are `.txt` files of task ids beside a `tasks.jsonl` whose rows carry `id` and `prompt` only — labels live in the judge, because task rows are learner material. (3) An adapter is a directory with `ADAPTER.md`, `exports.yaml`, and `.hermit/adapter.yaml` (metadata contract `"2"`) declaring `template` and `structure` (`learnable`/`fixed` with `format.max_bytes`) plus `.hermit/EVOLVER.md`; not a single `ADAPTER.md` beside a card. (4) SkillOpt inside Hermit is `evolver.name: skillopt` with eighteen documented parameters and a required `data.val`, not a separate `config.yaml` with invented keys. Hermit also documents run records (`steps.jsonl`, `learning_material/step_NNNN/`, `summary.json`, `output/report.md`, `checkout/`) and a workspace deploy that writes `AGENTS.md`/`CLAUDE.md` with a managed block naming `hermit/<id>/`. The theory under test is that the training layer can emit exactly that contract — every section, split file, label boundary, metadata section and record — and validate it without a network or a Hermit install, while keeping the kernel's own gate and version chain.
- **Hypothesis:** H-098: "optimization_accuracy >= 0.90"
- **Measurement Metrics:** optimization_accuracy >= 0.90
- **Experiment Design:** Measure `scripts/bench/bench_optimization.py`, extended from 52 to 78 independent checks. The 26 new checks cover the documented contract rather than a plausible one: the run config's required sections and the absence of unknown top-level keys; the three `.txt` split files resolve to unique task ids; `tasks.jsonl` rows carry exactly `id` and `prompt`; the generated `judge.py` loads and returns 1.0 for a satisfying answer and 0.0 for a missing one; `pipeline.py` declares `run(task, adapter) -> RunOutput` and reads the adapter through `Session(adapter).context()`; `.hermit/adapter.yaml` has `template`/`structure`, contract `"2"`, a valid slug, `ADAPTER.md` learnable with `max_bytes` and `README.md` fixed; `exports.yaml` declares `context: ADAPTER.md`; `.hermit/EVOLVER.md` and `task-info/README.md` exist; the SkillOpt export carries all eighteen documented parameters with their defaults, a required validation split, `evolver.name: skillopt`, `best_skill.md` byte-identical to the measured adapter, and a recorded parameter mapping; the method registry lists the nine documented Evolvers and refuses ACE; the loop writes `steps.jsonl`, `summary.json`, `output/report.md` and label-free learning material; preflight refuses a validation split below the gate; deploy writes `AGENTS.md`/`CLAUDE.md`, refuses a foreign non-empty workspace, and redeploys into a single managed block. The `--broken` control degrades the export to the pre-correction shape (legacy flat config, labelled task rows, missing `EVOLVER.md`), returns an empty method registry, skips records, makes preflight always pass, and removes the deployed instruction file; the same 78 assertions then run. Offline, deterministic, no Hermit install required: the judge is loaded against an injected `hermit.task` module exposing the documented `JudgeResult`/`RunOutput` shape.

- **Known Gaps:** The export is validated structurally, not by a live Hermit 0.1.0 install: key names, sections, split semantics and metadata are checked, but whether a given Hermit patch release accepts every value is only established by running `hermit check` in that environment, which this repo cannot do offline. The generated `pipeline.py` and `judge.py` import `hermit`, so their functional check injects a minimal stand-in module; it proves the judge's scoring logic, not the real framework's constructor signatures. `convert` (native plugin emission) is not reimplemented — the export provides the adapter directory `hermit convert` consumes. The kernel's textual budgets (`max_edit_chars`, `textual_lr`) have no Hermit parameter, so an export cannot carry them into a Hermit run; this is documented in the export README and the parameter mapping rather than silently approximated. The bench's broken control degrades the production code paths in memory, so it proves the checks can fail, not that an independent implementation of Hermit would behave identically.
