## Experiment: E-014 — The number belongs to the commit that owns it: versioning moves to commit time, and the pipeline stops adding commits

- **Date:** 09.10.2026
- **Status:** completed
- **Theory:** The E-010/E-012 design fixed the number AFTER a push, which needs
  a second commit to hold it — and the evidence shows what that costs. Two of
  the last four commits (`c81b533`, `00cb75b`) exist **only** to carry a
  version: no content, no message of their own, just `chore(release): version
  bump`. Worse, an authored commit that forgot to hand-bump (`0f76fb5`) kept
  the previous number in its tree and was tagged by position anyway, so the
  pointer and the tree disagreed. Both failures share one root cause: the
  number was produced at the wrong moment. A commit's position is known at the
  moment the commit is created — the hook chain runs before the object is
  written — so the number can be written by the commit that owns it, and the
  post-hoc repair disappears. What remains for the pipeline is what it can do
  without lying: read the tree of every commit the push carried, check it
  against that commit's position, and publish the tags. It never writes a
  version and never creates a commit; a number that does not match is a red
  job naming the exact number it should be, not a silent fix-up. The
  enforcement therefore moves to where the number is produced (a committed
  pre-commit hook, installed with `git config core.hooksPath .githooks`), and
  `--no-verify` stops being a loophole because the pipeline refuses what the
  hook skipped.
- **Hypothesis:** H-014: "consistency_accuracy >= 0.90"
- **Measurement Metrics:** consistency_accuracy >= 0.90
- **Experiment Design:** Inputs — the plugin repository at this commit, and its
  own git history and tags. Procedure — run
  `python scripts/bench/bench_consistency.py`, which evaluates independent
  doc/code-consistency claims and prints `consistency_accuracy=(x/y)`; three
  new checks pin the E-014 claim (the committed hook exists and this clone has
  it wired via `core.hooksPath`, the workflow contains no `git commit` and

  (falsifier)" check pins that the code under test still passes the full
  suite, which now includes hook tests that create real commits and pipeline
  tests that run the workflow's own shell against scratch repositories.
  Reproducibility — stdlib + git only, no network: the hook's position math is
  the same `rev-list --count` the pipeline verifies with, and the bench reads
  the tree and its refs as they are, independent of this record (E-001).

- **Known Gaps:** the hook is installable, not installed by git itself — a
  fresh clone that never runs `git config core.hooksPath .githooks` produces
  commits with the previous number, and the pipeline then refuses them (loud,
  with the install line in the error) instead of repairing; the bench checks
  this clone's `core.hooksPath`, so a missing installation is visible before a
  push. `git commit --no-verify` bypasses the hook by design — same outcome:
  the pipeline refuses the number. The hook rewrites seven version-owned files
  and stages them, so an author with unstaged edits to one of those files is
  refused before any write (stage your work first — the number is never
  written over uncommitted content). Merge commits get the number of the
  commit being created — by the author's `git commit` when the merge
  conflicts (MERGE_HEAD present: the union), by `.githooks/post-merge`'s
  amend when `git merge` creates it clean (both verified in the hook tests;
  a merge made with `--no-verify` is refused downstream). Commits
  from a tool that bypasses hooks (amend, rebase, cherry-pick) inherit their
  position's number only if the hook runs — `git rebase` does run it, and
  anything that lands a wrong number is refused by the pipeline with the
  number it should be. The merge path needed one discovery beyond the hook:
  `git merge` creates its commit from the tree it merged with NO pre-commit,
  and the tree is written before pre-merge-commit or prepare-commit-msg run,
  so a staged write in either is dropped — verified by probe, not assumed.
  `.githooks/post-merge` therefore writes the merge's number the moment the
  commit exists (removing MERGE_HEAD first, which git deletes only after this
  hook and which `git commit --amend` refuses to work under) and amends it in
  place; a conflicted merge needs no amend, because the author's own
  `git commit` runs the pre-commit hook with MERGE_HEAD present. Both shapes
  are covered by hook tests against throwaway repositories. The
  `scripts/bump-version.py --position/--set-version`
  write modes stay (the hook calls them); only the workflow stops calling
them. The last two bot commits and the stale `0f76fb5` were this record's
evidence; when the day's nine commits were squashed into one, they left with
their tags (v0.1.16 … v0.1.18) — the cost they embodied is written down here
and in docs/VERSION-HISTORY.md rather than carried forward as commits.
