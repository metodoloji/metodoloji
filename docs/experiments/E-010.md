## Experiment: E-010 — A version-only CI: every commit on main raises the plugin version, and the pipeline itself enforces the bump

- **Date:** 08.10.2026
- **Status:** completed
- **Theory:** Self-hosting discipline (P4 + ASLA #60): the plugin ships gates to
  projects, so its own release number deserves a mechanical instrument too.
  Version skew is exactly the failure class check-plugin §6d3 already names
  ("stale marketplace caches serve old trees under an unchanged version
  number") — but §6d3 only detects skew AFTER a human remembers to bump; the
  increment itself had no owner (v0.1.0 → v0.1.5 happened by hand). The
  repository currently CLAIMS "no CI workflow" in four live places (README,
  GUIDE, KILAVUZ, and a test docstring) while simultaneously paying for six
  local audits that nobody is forced to run — the honest fix is one dedicated
  pipeline whose only job is the increment, leaving the audits local and
  updating every claim that pipeline makes false. Design: a stdlib bump
  script that refuses to act on manifest skew (the enforcement half), plus a
  single GitHub Actions workflow that runs it on every push to main and adds
  the push's commit count (`github.event.before..sha`) to the patch segment,
  so N commits in one push raise the version by N — one increment per commit,
  with the bot's own push kept out of the loop (GITHUB_TOKEN pushes do not
  re-trigger workflows; a `[skip-version]` message guard covers manual
  re-runs).
- **Hypothesis:** H-010: "consistency_accuracy >= 0.90"
- **Measurement Metrics:** consistency_accuracy >= 0.90
- **Experiment Design:** Inputs — the plugin repository at this commit. Procedure —
  run `python scripts/bench/bench_consistency.py`, which evaluates independent
  doc/code-consistency claims and prints `consistency_accuracy=(x/y)`; two new
  checks pin the E-010 claim (the workflow exists, declares `contents: write`,
  drives the bump script and contains NO test/audit step — CI is version-only
  — while README/GUIDE/KILAVUZ no longer deny CI's existence; and the bump
  script's behavior is covered by tests), and the suite's pytest falsifier
  covers the new regression tests. Control — the bench's own "pytest suite
  green (falsifier)" check pins that the code under test still passes the full
  suite. Reproducibility — stdlib only, no network, deterministic (a fixed tree
  yields a fixed x/y); the measurement reports the tree as it is, independent
  of this record (E-001).
- **Sample Size n:** 63 (informational — the gate parses the denominator from

- **Code Scope:** .github/workflows/version-bump.yml, scripts/bump-version.py, scripts/tests/test_bump_version.py, scripts/tests/test_selfcheck_scripts.py, scripts/bench/bench_consistency.py, README.md, GUIDE.md, KILAVUZ.md

- **Known Gaps:** the bump runs on PUSHES TO MAIN only — a feature-branch
  commit bumps nothing until it lands (by design: branch versions would fork
  the marketplace number). One push carrying N commits is ONE workflow run
  that adds N (rev-list `before..sha`), which equals per-commit increments in
  version arithmetic but is not one RUN per commit; a force-push whose
  `before` SHA no longer exists falls back to +1 (monotone, never silent).
  The bot commit is kept out of the loop by the platform rule (GITHUB_TOKEN
  pushes do not re-trigger workflows) AND a `[skip-version]` message guard —
  if both were bypassed (e.g. a human re-run pushing with a PAT) the version
  would bump twice, which stays monotone and therefore harmless rather than
  wrong. A branch-protection rule that rejects the bot's push turns the job
  RED (loud enforcement, never a silent skip). Manifest skew at bump time
  makes the script exit non-zero: the pipeline fails BEFORE writing anything.
  The audits themselves (pytest, check-plugin, the rest) intentionally stay
  local — this CI never runs them.
