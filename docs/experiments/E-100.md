## Experiment: E-100 — A live Hermit install, not just a reading of its documentation

- **Date:** 02.11.2026
- **Status:** completed
- **Theory:** E-098 and E-099 corrected the exports from the two upstreams' documentation, and both records stated the same limit: the contract was validated structurally, never by running the tools, because this kernel has no network and no model. Installing them shows what reading could not. Four classes of defect appeared in one session. (1) Hermit's PyPI wheel 0.1.0 has no `hermit/agent` package, so the documented quickstart runs only from the source checkout; installing from PyPI leaves `hermit check` failing with `No module named 'hermit.agent'`. (2) Hermit 0.1.0 is not Windows-portable in five places: `agent/base/login.py` imports `fcntl` unconditionally (every command dies), `sandbox.py` keeps `SystemRoot` out of the sandbox allowlist and compares environment names case-sensitively while Windows stores them upper-cased (a child cannot start Winsock: `WinError 10106`), `isolate.py` hands the worker its result through `subprocess(..., pass_fds=...)` (unsupported on Windows), `trainer/material.py` symlinks `learning_material/current` (a privilege an ordinary account lacks, `WinError 1314`), and `tree.py` removes an exported adapter whose git objects are read-only (`PermissionError`). (3) The generated `run.yaml` had two defects the real `hermit check` refused or silently disabled: `task_info` was nested under `data` (an unknown framework key), and `sandbox.env: []` handed the acting worker no environment at all, so the pipeline could never reach its endpoint. (4) The SkillOpt CLI accepts the six-section native config completely and stops only at `env.name`, because no environment adapter is generated. The theory under test is that a pinned, patched, project-local install of both tools makes those claims mechanically checkable — the patch's fixes are present and the generator's fixes are in the emitted file — and that the same predicates fail against the upstream text as published for the patch half.
- **Hypothesis:** H-100: "upstream_accuracy >= 0.90"
- **Measurement Metrics:** upstream_accuracy >= 0.90
- **Experiment Design:** Measure `scripts/bench/bench_upstream.py`: twelve independent structural checks over the pinned checkout at `vendor/hermit` and over the run configuration `optimization/bridges/hermit.py` renders. Eight checks pin the five Windows defects and the shim they were fixed with: no module-scope `import fcntl` and an `msvcrt` fallback present; every `fcntl.flock` call routed through the shim; the sandbox allowlist carrying `SystemRoot`, `SystemDrive`, `windir`, `TEMP`, `TMP`, `PATHEXT`, `COMSPEC`; a case-folded environment comparison; a `HA_RESULT_PATH` carrier in both `worker.py` and `isolate.py`; `pass_fds` supplied only on the non-Windows branch; a directory-junction fallback in `material.py`; a read-only-clearing `onexc` in `tree.py`. One check pins that the patch names all six files it edits. Three checks render a real `run.yaml` through the bridge from a temporary spec and assert that `task_info` is top level, that `enforce: best_effort` and `env: null` are present, and that `data` carries exactly its seven documented keys. The `--broken` control copies the six patched files into a temporary tree and reverses the patch with `patch -R -p1`, then runs the same twelve predicates against upstream as published; the generator checks stay passing there by construction, so the control can only reach 4/12. Offline, deterministic, stdlib plus the project's own bridge. No model, no network, no API key.
