## Experiment: E-030 — §2c must demand the two-part verify pattern its sibling §4 already demands, and its documented size must match its wiring

- **Date:** 12.10.2026
- **Status:** completed
- **Theory:** `check-custom.sh` §4 audits its gate-enforcing set for a TWO-part
  pattern: a verify marker (`VERIFY`/`VERIFICATION`/`DOGRULAMA`) AND the
  companion phrase that names the repair when the file is missing (`error and
  recreate` / `hata ver`). `check-plugin.sh` §2c audits the 17 producer BRIDGE
  surfaces for only the FIRST half. E-018 widened §2c to the whole producer set
  and left this exact gap in its own Known Gaps — "§2c now demands the VERIFY
  marker on all 17 producers but still does not demand the companion 'error and
  recreate' phrase there … widening that too is a candidate follow-up". It is a
  real hole, not a cosmetic one: the recreate half is what forces the LLM to
  re-check the created record via the terminal instead of moving on, so a
  producer could drop it while §2c kept printing HEALTHY — the same "a guarantee
  exists only where its wiring is" class E-018/E-020/E-021/E-024/E-027 named,
  here with two audits of one class stranded at two different strengths.
  Measured on this tree: all 17 producers already carry both halves, so widening
  §2c is a pure pin (no BRIDGE edit needed) that only fires when a producer
  regresses. The same reading surfaced a second, independent drift: the
  GUIDE.md/KILAVUZ.md check-map still prints "#2c bridge VERIFY (13 skills)"
  although §2c audits 17 — the count E-018 changed in the audit but not in the
  map. The fix makes §2c demand both halves with §4's exact marker vocabulary,
  corrects the check-map to §2c's real count and strength, and pins all of it —
  including §4's own strength and §4's set living inside §2c's — in one bench
  check.
- **Hypothesis:** H-030: "consistency_accuracy >= 0.90"
- **Measurement Metrics:** consistency_accuracy >= 0.90
- **Experiment Design:** Inputs — the plugin repository at this commit.
  Procedure — run `python scripts/bench/bench_consistency.py`, which evaluates
  independent doc/code-consistency claims and prints
  `consistency_accuracy=(x/y)`; one new check pins the E-030 claim (it parses
  §2c's `PRODUCER_KEY` map and §4's `KOPRU` set out of the two scripts, demands
  §2c's source runs the two-part gate with §4's exact marker vocabulary, demands
  §4 still runs it, demands §4's set is a subset of §2c's, re-evaluates both
  halves on every producer's own BRIDGE TOML, and pins the GUIDE/KILAVUZ
  check-map count to §2c's producer count), plus the regression test by name.
  Control — the bench's own "pytest suite green (falsifier)" check pins that the
  code under test still passes the full suite, which now includes the E-030 test
  (`test_bridge_verify_pattern_parity_with_the_custom_audit`). The probe is
  falsifiable by construction: reverting §2c to the verify-only gate turns the
  new bench check red (`check-plugin.sh §2c dropped the 'error and recreate'
  half; check-plugin.sh §2c marker vocabulary drifted from §4`), stripping the
  phrase from one producer TOML turns it red
  (`bmad-dev-story: no 'error and recreate' phrase in
  workflow.activation_steps_append`), and reverting the check-map to "13 skills"
  turns it red (`GUIDE.md check-map says #2c audits 13 skills, but §2c audits
  17`). The real audit agrees: with the phrase stripped from
  `custom/bmad-dev-story.toml`, `check-plugin.sh` §2c reports `MISS: bmad-dev-story
  (verify+error pattern missing in BRIDGE[workflow.activation_steps_append]…)`
  and its problem count rises to 1, where before E-030 it stayed green.
  Reproducibility — stdlib only, no network, deterministic: the check reads the
  tree, the scripts and the BRIDGE TOMLs as they are; a fixed tree yields a fixed
  x/y; the measurement reports the tree as it is, independent of this record
  (E-001).
