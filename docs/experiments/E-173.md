## Experiment: E-173 — The session edge carries the configured language

- **Date:** 2026-11-16
- **Status:** completed
- **Record Kind:** contract
- **Theory:** Measured 2026-11-16 on this tree: resolve_config.py resolves core.communication_language=Turkish from docs/config.toml (orient.py prints lang=Turkish), yet a session answers in English. Two surfaces were why. First, the session edge — the one context every runtime delivers — carried no language clause: bootstrap.sh builds its context from roots, chain, tools and init hint, and audit.FIXED_SESSION_CONTEXT adds shell discipline only, so the configured language reached the model only when a skill ran orient.py. Second, three shipped skills named the plugin's own config files as the language source (bmad-research-experiment, bmad-workflow, bmad-customize), which resolves to the plugin's English defaults and ignores the project layer — a second owner for a value the resolver already owns (E-146/E-147).
- **Hypothesis:** H-173: "session_language_accuracy == 1.0"
- **Measurement Metrics:** session_language_accuracy == 1.0
- **Experiment Design:** Inputs: the shipped engine (hooks/engine/main.py session_start) and the shipped skill surfaces, plus the pre-fix tree at git b94113d. Procedure: scripts/bench/bench_language_context.py builds one throwaway project per probe, runs the engine's session_start against it with CLAUDE_PROJECT_DIR set, and requires the injected context to carry both resolved values in their own clauses; expected values are asked of the tree's own resolve_config.resolve(), never restated in the bench. One further probe derives the population of shipped SKILL.md files that name a language key and requires none of them to name a plugin-root config file as that key's source. Control: --broken runs the same probes against b94113d, whose session_start carries no language clause and whose skills name the plugin config. Reproducibility: stdlib only, offline, deterministic (each probe is a fresh temp project).
