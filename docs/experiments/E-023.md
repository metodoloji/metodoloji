## Experiment: E-023 — The audit must go green, and its own proof must cover the provenance gate

- **Date:** 10.10.2026
- **Status:** completed
- **Theory:** Three pieces of behavior evidence, all measured on this tree today:
  (1) `sh scripts/check-plugin.sh` exits **1 with 3 problems** — `E-015`,
  `E-016`, `E-017` are reported `[ERROR] approved but --verify failed (FORGED?)`.
  Their tokens were signed by a key outside this machine's trust ring, so the
  audit can never reach HEALTHY (E-001..E-005 already carry the documented P11
  `Re-Measured-By:` marker; these three were never re-measured). The record has
  the cure — re-run the same measurement under this machine's key and declare
  it — but nothing forces the corpus to be *consistent* while three errors sit
  in the audit every run.
  (2) `check-plugin.sh --negtest` proves 8 sections catch breakage (8/8 OK) —
  but stage-by-stage: `§6a`, `§2b`×2, `§1b`, `§6c`, `§6d`, `§6e`, `§6g`. **No
  stage exercises `§3`, the token/provenance gate**, which is the very section
  that produced the three errors above. The gate that decides "this record is
  forged" is the one gate the negative test never breaks. Worse,
  `total_stages = 8` and the closing `all {total_stages} … successful` are both
  driven by the variable alone: deleting a stage header leaves the run printing
  `[OK] all 8 negtest stages successful` while only seven ran. Nothing pins the
  declared count to the headers that exist.
  (3) The advertised count has already drifted: `GUIDE.md:564` and
  `KILAVUZ.md:563` both promise **"7 stages"** while the script ships 8 (§6g was
  added later) — the stale-count class E-013/E-014 named, in the runbook a
  reader follows to run the negative tests. No check compares the docs' number
  to `total_stages`.
  (4) the script's own declarations of the same number are unfalsified too:
  its header (`negative tests, N stages`) and its coverage-map comment — which
  pointed at `docs/SELF-CHECK.md`, a file that is **not in the tree** (a live
  surface naming a missing file, the E-019 class).
  The root cause is once more the E-018/E-019/E-020/E-021 class — a guarantee
  exists only where its wiring is — applied twice over: the *repair* is
  documented but unused, and the *negative test* is a count nobody can falsify.
  The fix follows the same three moves those records used: (a) do the P11
  repair properly — re-measure the shared claim under this machine's key in a
  new record and add the plain `Re-Measured-By:` line to each old record (docs
  only; the token is not bound to it, so the old decisions stay as written);
  (b) add negtest stage 9/9, which byte-corrupts a record's `Gate Evidence` and
  demands §3 report `approved but --verify failed` with exit 1, then restores;
  (c) add a bench check that pins `total_stages` to the stage headers that
  actually exist (indices 1..N, one of them naming §3) and to both runbooks'
  advertised count, so the suite cannot silently shrink and the docs cannot
  silently go stale again.
