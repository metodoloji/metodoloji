## Experiment: E-013 — The release line: block boundaries are arithmetic, and only a human declares a major line

- **Date:** 09.10.2026
- **Status:** completed
- **Theory:** E-012 made the number a property of the commit and repaired the
  chain, but left the boundary undefined — nothing said when `0.2.0` or `1.0.0`
  arrives, so `0.1.1312` was legal, the patch grew without bound, and the
  minor/major slots carried no meaning and no owner. Two facts shape the fix
  rather than taste. (1) Small increments CAN be owned mechanically: a count
  the repository can check is honest as long as it is total, monotone and
  invertible, which is exactly what a block mapping gives — position 100 IS
  0.2.0, position 200 IS 0.3.0, and nobody has to schedule a release for the
  boundary to be defined. (2) A major number cannot be owned by a counter: in
  semver `0.x` says "anything may change", so `1.0.0` is a statement about
  maturity that only a human can make — it must be declared, and a declaration
  must be checkable (hence a marker in the commit, not a convention nobody can
  verify). The same reasoning defines the failure modes: a number the mapping
  cannot produce (`0.1.150`, `0.9.3`) is a claim about commits that do not
  exist, and an undeclared major line is a claim about a maturity decision
  nobody made — both are refused loudly with the number they should have been.

- **Measurement Metrics:** consistency_accuracy >= 0.90

- **Known Gaps:** the block rule means a minor bump carries no feature
  meaning — `0.2.0` says "100 commits have passed", not "something changed
  incompatibly"; a maintainer who wants a meaningful number must declare a
  major line. A declared line's patch is only constrained by the count: the CI
  computes `X.Y.<commits since vX.Y.0>` and a hand-written number above that
  position is refused (it would walk backwards), so a declared line's tree is
  repaired rather than trusted, but a declaration cannot be undone — the v1.0.0
  tag stays. The declaration is read from the head commit only: pushing the
  marker together with unrelated commits evaluates the head, so a declaration
  must be the push's tip. `scripts/versioning.py` is deliberately git-free and
  cannot prove a position is real; the enforcement lives where git does (the
  CI's tag step and the bench's chain check), and `release-tags.py` still
  anchors repairs to the position-0 commit of the automatic line — a declared
  line's history would need its own anchor, which is out of scope until one
  exists. The intermediate commits a push carries get position-named tags while
  their trees still hold the previous number (the convention documented in
  docs/VERSION-HISTORY.md); only the release commit's tree matches its own
  number. The block size 100 was chosen so every published tag keeps its
  meaning (a smaller block would have re-pointed v0.1.10..v0.1.14) and the
  patch stays two digits; changing it later is itself a renumbering, so it is
  pinned in code, docs and tests.
- **Amendments:** E-012's `--set-patch`/`with_patch`/`next_patch` are superseded
  by `--position`/`--set-version` and the positional `--by` (the rule now owns
  both directions), and the E-010/E-012 test-name pins in the bench follow the
  renamed tests. Historical records keep their original wording — they describe
  the repo as it was.
