## Experiment: E-009 — Close the file-decode seam: invalid UTF-8 in an external file must be an honest refusal, never a traceback

- **Date:** 08.10.2026
- **Status:** completed
- **Theory:** The same doctrine as E-002/E-003/E-006/E-007 (a malformed input
  from outside must END in a machine-readable decision), one surface higher:
  the FILE seam. External files (state, config, markers) are written by other
  tools, editors, merges and humans; a file that is not valid UTF-8 raises
  `UnicodeDecodeError`, which is a `ValueError` but NOT a
  `tomllib.TOMLDecodeError` nor a `json.JSONDecodeError` — so every handler
  written as `except (TOMLDecodeError, OSError)` or
  `except (OSError, JSONDecodeError)` misses it. Behavior probing with binary
  payloads (`\xff\xfe\x00…`) proved the class on five production surfaces:
  (1) workflow CLI — a binary `<slug>.state.json` crashes `list`, `status`,
  `next`, `history` and `flag` with a traceback (store.read_state's except
  tuple); (2) `resolve_config` — a binary project config layer escapes the
  TOMLDecodeError handler inside `load_toml`; (3) `resolve_customization` —
  same shape on `customize.toml`; (4) `skeleton --status/--install` — a binary
  `.metodoloji/initialized` escapes `read_marker`'s `except OSError`;
  (5) `orient` (both modes) crashes through `_skeleton.status`. Text-garbage
  TOML and text-garbage JSON are already handled — only the DECODE class
  escapes. The fix extends each existing except clause along its own honest
  policy: the workflow store keeps its documented fail-open contract
  (undecodable = corrupt) while `state_is_corrupt` (E-008) reports the file as
  CORRUPT; the config loaders keep their warn/exit-1 policy with the codec
  message; the skeleton gains a distinct `unreadable` problem so a binary
  marker is never reported as merely "missing".
- **Hypothesis:** H-009: "consistency_accuracy >= 0.90"
- **Measurement Metrics:** consistency_accuracy >= 0.90
- **Experiment Design:** Inputs — the plugin repository at this commit. Procedure —
