## Experiment: E-155 — The published release chain obeys the count rule

- **Date:** 2026-11-14
- **Status:** completed
- **Record Kind:** contract
- **Theory:** scripts/versioning.py owns the number: version(position) = 0.<1+position//100>.<position%100>, anchored at the first commit, and the tag chain is supposed to publish it. Measured 2026-11-14 at HEAD (position 191, every manifest says 0.2.91): seven published tags sit one commit late (v0.2.30 on #134, v0.2.34 on #135 through v0.2.39 on #140), positions 130 and 140 carry no tag of their own (the checker names the number hole as v0.2.40), and positions 148..191 were never published at all — the newest pointer, v0.2.47, is 44 commits behind a tree that already says 0.2.91. The tree cannot be un-committed and rewriting commits would invalidate every SHA; what is wrong is where the published POINTERS sit, and E-012 already documents that a retro-assigned tag means 'this commit is the Nth commit', not the string inside that tree. Re-pointing tags is therefore the sanctioned repair, done locally and not pushed: publishing is a separate, forced update this task does not authorize.
- **Hypothesis:** H-155: "release_tag_accuracy == 1.0"
- **Measurement Metrics:** release_tag_accuracy == 1.0
- **Experiment Design:** Inputs: the local repository (git history + tags) at this commit, plus docs/experiments/E-155/raw/control-tags.json — the exact tag-to-commit map captured BEFORE the repair, which is the control arm. Procedure: scripts/bench/bench_release_tags.py runs five probes over a derived state (ordered commits, position map, tag map): (1) every position 0..N carries its rule tag on the rule's commit; (2) no release-looking tag points outside the enumerated history; (3) every release-looking tag name is a number the rule can produce (versioning.auto_position); (4) the newest release points at a tree whose own manifests hold that number in all five version-owned files; (5) the newest release is the HEAD position, so the published chain reaches the commit that carries the current version. --broken evaluates the same five probes against the captured pre-repair map, so the control shows the drift this repair removes. Reproducibility: stdlib + git, offline, deterministic; tags are read with one for-each-ref.

Pushing is deliberately out of scope — a re-pointed tag cannot fast-forward, so publishing is a forced `--push` the task did not authorize. (2) A retro-assigned tag names the commit's position, not the string inside that tree; trees written before the rule may carry an older string, which is the convention E-012 documents, so only the newest release is required to hold its own number. (3) The bench reads the local repo with `for-each-ref`; a clone fetched without tags measures an empty chain and fails loudly rather than skipping. (4) `release-tags.py` offers `--plan` but no separate dry-run of the write set; the plan printed before applying is the evidence of what changed, and the captured control map makes the before-state re-measurable.

- **Control:** `--broken` evaluates the captured pre-repair map (`docs/experiments/E-155/raw/control-tags.json`) and measures `0.60 (3/5)`: positions and HEAD-reach fail, containment and producibility pass. That is the drift this repair removes, replayable offline.
